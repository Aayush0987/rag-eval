# RAG Eval

A general-purpose evaluation and observability tool for RAG systems. Submit
`(question, contexts, answer, ground_truth?)` triples and get faithfulness,
answer relevance, and context precision/recall scores from two independent
implementations — a from-scratch pipeline and [RAGAS](https://github.com/explodinggym/ragas) —
side by side, plus regression tracking across runs over time. The
comparison framework used is [RAGAS](https://github.com/explodinggradients/ragas).

## Why two implementations

The core metrics (faithfulness, answer relevance, context precision/recall)
are built from scratch rather than just wrapping RAGAS, and RAGAS itself is run on
the same inputs for comparison. The point isn't to reinvent RAGAS — it's to
understand what these metrics are actually measuring by building them, and
to have a second opinion to sanity-check against. See
[`docs/ragas_comparison.md`](docs/ragas_comparison.md) for the results of
that comparison; the short version is that the two agree closely on
faithfulness but diverge meaningfully on answer relevance, and that
divergence is informative, not a bug in either one.

## What each metric measures

**Faithfulness** — of the claims made in the answer, what fraction are
actually supported by the retrieved context? Catches hallucination. Custom
implementation: an LLM decomposes the answer into atomic claims, then a
local NLI cross-encoder (`cross-encoder/nli-deberta-v3-base`) classifies
each claim against the context as entailment/neutral/contradiction — only
`entailment` counts as supported. This is deliberately *not* a second LLM
call, both to test whether a dedicated NLI model is a reasonable substitute
and to keep the metric cheaper and faster than an all-LLM pipeline.

**Answer relevance** — does the answer actually address the question asked?
Two independent signals: (a) cosine similarity between question and answer
embeddings (`all-MiniLM-L6-v2`) — cheap, but only measures topical
alignment, not correctness; (b) an LLM-as-judge score that explicitly
penalizes factual errors and evasiveness as part of "relevance." These two
regularly disagree (see the comparison report) — the embedding approach
can't tell a confidently wrong answer from a correct one, since both are
topically on-target.

**Context precision** — of the retrieved chunks, what fraction were
actually useful, weighted so that useful chunks ranked earlier count more
(this rewards the retriever for good ranking, not just recall). Computed by
having an LLM judge each chunk's relevance to the question (and reference
answer, if given), then averaging precision@k over the relevant ranks.

**Context recall** — of the facts needed to produce the reference answer,
how many are actually present somewhere in the retrieved context? Requires
a ground truth. The reference answer is decomposed into atomic statements,
and each is checked for whether it's attributable to the retrieved context.

## Custom vs RAGAS: validation results

Full analysis in [`docs/ragas_comparison.md`](docs/ragas_comparison.md),
generated by `backend/scripts/compare_ragas.py` against the labeled set in
`data/sanity_check/examples.jsonl` (6 good/bad pairs). Headline results:

- **Faithfulness**: near-perfect agreement (both separate good/bad
  perfectly: 1.000 vs 0.000 on this set). Validates that a local NLI model
  is a viable, cheaper substitute for a second LLM-as-judge call.
- **Answer relevance**: sharp divergence. RAGAS's `answer_relevancy` only
  measures question/answer semantic alignment and stayed high (0.45-1.00)
  even on hallucinated answers; the custom LLM-judge metric, which
  explicitly penalizes factual errors, correctly dropped to ~0.00 on every
  bad example. Neither is "wrong" — they're answering different questions —
  but a dashboard that doesn't distinguish them would be misleading.
- **Context precision/recall**: by design, near-identical within each
  good/bad pair (same retrieved context, only the answer changes) — these
  metrics score retrieval quality, not generation quality. One real gap:
  custom context recall averaged 0.742 vs RAGAS's 1.0, worth auditing
  further on a larger test set.

## Regression testing — example walkthrough

Verified live: submitted a baseline run (`"Water boils at 100°C at sea
level"` — correct), marked it as baseline, then submitted a second run with
a regressed answer (`"Water boils at 40°C at sea level"`). `GET /regression`
correctly flagged the example, with per-metric deltas:

| Metric | Delta |
|---|---|
| Faithfulness | -1.00 |
| Answer relevance (LLM) | -0.80 |
| Context precision | 0.00 |
| Context recall | 0.00 |

A drop of more than 0.1 on any metric flags an example as regressed
(`REGRESSION_THRESHOLD` in `backend/app/metrics/regression.py`). The
regression endpoint also reports questions present in only one of the two
runs, rather than silently dropping them, since a shrinking test set is
itself worth noticing.

## Dashboard

Three views: run history (with a "mark as baseline" action), per-example
detail (custom vs RAGAS scores side by side, expandable raw judge output),
and a regression view (pick a baseline + a run, see aggregate and
per-example deltas with regressions highlighted). Screenshots aren't
included here — this session had no browser/screenshot tool available, so
the UI was verified via a clean TypeScript build and by matching the
frontend's types against the backend's actual response shapes, not by
looking at it. Worth a look at `localhost:5173` before calling this phase
done.

## Known limitations

- **LLM-as-judge cost and latency.** Every example triggers several LLM
  calls (claim decomposition, per-claim/chunk/statement judging), and RAGAS
  adds its own separate set on top. A batch of a few dozen examples can
  take minutes.
- **Groq free tier rate limits, hit live during development.** There's both
  a per-minute cap (8,000 TPM) and a per-day cap (200,000 TPD). The
  per-minute limit is handled with retry + exponential backoff
  (`app/llm/groq_client.py`); the daily cap is not reasonably retryable and
  was exhausted during this build's own testing. A real evaluation workload
  of hundreds of examples needs a paid tier or multi-day spreading.
- **Gemini fallback.** If `GEMINI_API_KEY` is set, judge calls fall back to
  Gemini (`gemini-flash-lite-latest`, via its OpenAI-compatible endpoint)
  when Groq stays rate-limited; RAGAS retries the whole evaluation on Gemini
  if any metric comes back NaN. Gemini's free tier is about 15 requests per
  minute, so large batches still run slowly. Some Gemini preview models have
  far tighter caps (`gemini-3.6-flash` allowed only 20 requests per day).
- **LLM-as-judge biases.** Known failure modes — position bias, verbosity
  bias, self-preference bias (the judge favoring answers phrased the way it
  would phrase them) — apply to every LLM-judge metric here and haven't
  been independently measured against this pipeline's specific prompts.
- **Custom vs RAGAS is not a ground-truth comparison.** Agreement between
  the two is weak evidence both are "right" (they could share the same
  blind spot); divergence tells you they measure different things, not
  which one is correct. Treat the comparison report as a documentation aid,
  not a proof of correctness.

## Running it

Backend:
```
cd backend
cp .env.example .env   # add GROQ_API_KEY (and optionally GEMINI_API_KEY as fallback)
uv sync
uv run uvicorn app.main:app --loop asyncio
```

`--loop asyncio` is required: uvicorn's default `uvloop` can't be patched by
RAGAS's internal `nest_asyncio` call, and every RAGAS evaluation inside the
server fails with `Can't patch loop of type uvloop.Loop` without it. Don't
delete `rag_eval.db` while the server is running.

Frontend:
```
cd frontend
npm install
npm run dev
```

Sanity-check the custom metrics against the labeled set:
```
cd backend
uv run python scripts/sanity_check.py
```

Regenerate the custom-vs-RAGAS comparison report:
```
cd backend
uv run python scripts/compare_ragas.py
```

See [`PROGRESS.md`](PROGRESS.md) for build status against the original
phase-by-phase plan.
